## Схема одного круга

```text
задача человека
  → сообщения system + user
  → запрос к модели с описаниями разрешённых инструментов
  → ответ модели
      ├─ обычный текст без tool_calls → кандидат на завершение
      └─ tool_calls
          → программа разбирает имя и аргументы
          → программа находит функцию и запускает её
          → результат добавляется как role: tool
          → следующий запрос к модели с обновлённой историей
```

В `v0.ts` сообщения создаются в строках 97–107, обращение к API — в
`chat` (строки 26–35), а повторение шагов — в строках 109–131. Модель
выбирает, нужен ли инструмент, но сама функцию не запускает: это делает
`tools[call.function.name].run(args)` в строке 125. Результат возвращается
модели через сообщение `role: tool` в строке 129.

В `core.ts` тот же порядок вынесен в `runAgent` (строки 24–95). Вокруг
цикла добавлены:

- `gate` — обязательная проверка результата кодом, а не обещанием модели;
- журнал шага, времени и токенов;
- `maxSteps` — верхняя граница числа обращений к модели.

## Пять понятий

### Модель

Модель — сервис, который получает историю сообщений и описания инструментов,
а возвращает текст или структурированную просьбу вызвать инструмент. В этом
примере модель не получает прямой доступ к файлам или терминалу.

### Сообщение

Сообщение — один элемент истории обмена. В примере есть `system` с правилами,
`user` с задачей, `assistant` с ответом модели и, если был вызов, `tool` с
результатом выполненной функции. Следующий запрос получает накопленную
историю, поэтому модель видит результат своего предыдущего действия.

### Инструмент

Инструмент — обычная функция программы плюс описание её имени, назначения и
параметров для модели. В `v0.ts` это `read_file`, `write_file` и
`run_command`. Описание помогает модели выбрать функцию, но не заменяет
проверки аргументов в самой программе.

### Цикл

Цикл — повторение последовательности «запрос модели → возможные инструменты
→ результаты в истории». Он продолжается, пока модель не ответит без
`tool_calls` или пока не сработает лимит шагов. Один вызов инструмента — ещё
не конец работы: модели может понадобиться увидеть результат и выбрать
следующее действие.

### Проверка завершения

Проверка завершения — отдельное условие, которое подтверждает результат.
В `core.ts` модель может написать, что закончила, но `gate()` сам проверяет
состояние и либо принимает ответ, либо возвращает модели отчёт об ошибке для
исправления. Поэтому слова «готово» сами по себе не доказывают, что файл
создан, структура верна или PDF действительно собран.

## Разбор одной строки журнала

Если журнал содержит:

```text
шаг 1: read_file src/article.txt
```

это означает: модель выбрала инструмент `read_file` и передала аргумент
`path: "src/article.txt"`. Компьютер должен был разобрать JSON аргументов,
найти зарегистрированную функцию `read_file`, прочитать этот файл и добавить
полученный текст в историю как `role: tool`. После этого следует новый запрос
к модели.

В реальном проекте такой вызов будет разрешён только после проверки имени
документа и пути. Пример из `v0.ts` показывает механику, но его прямые
`readFileSync`, `writeFileSync` и `execSync` не являются безопасной политикой
доступа для нашего агента.

## Маленький учебный опыт

Вымышленный ответ модели:

```text
Вызови read_file с path = "src/article.txt".
```

Сам ответ ничего не читает. Участок программы, который превращает просьбу в
действие, выглядит так (сокращённо по `v0.ts`, строки 120–129):

```ts
for (const call of reply.tool_calls) {
  const args = JSON.parse(call.function.arguments)
  const result = tools[call.function.name].run(args)
  messages.push({ role: 'tool', tool_call_id: call.id, content: result })
}
```

Полезный вывод опыта: модель выбирает `read_file`, компьютер выполняет
функцию, а результат возвращается модели отдельным сообщением. В нашей
реализации перед `run` должны появиться проверки разрешённого инструмента,
аргументов и пути.

## Что перенесём в учебный проект

Переносим простую последовательность сообщений, явные описания инструментов,
возврат результата в историю, ограничение числа шагов и проверку результата
кодом. Не переносим без изменений произвольное чтение и запись файлов,
запуск терминала и доверие к тексту «готово»: это ограничено правилами
`GUIDE.md` и будет реализовано отдельными задачами.
