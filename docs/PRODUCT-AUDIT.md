# Аудит проекта и план перевода в продуктовую версию

Дата аудита: 26 октября 2026 года. Ветка: `dev`. Аудит только читает код и запускает проверки; файлы проекта не менялись, кроме этого документа.

## 1. Итог

Проект работает как учебный конвейер для одного разработчика: статья → черновик → утверждение человеком → PDF. Сборка и typecheck проходят. Но продуктом это пока не назвать:

- 9 из 12 проверочных скриптов падают.
- Редактор работает только в `vite dev`, в сборке его API нет.
- Из браузера нельзя запустить агента: форма на главной только показывает введённую ссылку.
- Нет README, тестов, линтера и CI.
- Рабочая копия содержит чужие незакоммиченные изменения (см. раздел 5).

Перевод в продукт начинается с решения о цели (раздел 6). От него зависит, нужны ли сервер, аутентификация и хостинг.

## 3. Пробелы

### 3.1. Продукт и UX

- **Главная страница учебная, а не продуктовая.** В `src/App.tsx` служебный текст: «Первый экран готов», «Simple Claw подключим на серверном шаге». Заголовок вкладки в `index.html` — «PDF-агент».
- **Форма «Сохранить ссылку» ничего не делает.** Она выводит введённую строку. Запуска агента, статуса и результата в интерфейсе нет.
- **Редактор недоступен в сборке.** `worksApi()` в `vite.config.ts` работает только при `apply: 'serve'`. В `npm run build` панель «Работы» запрашивает `/api/works`, которого нет. (По коду, в сборку не запускал.)
- **Нет состояний ошибок и пустых состояний на главной.** Ошибки видны только в консоли или в ответе API.
- **Нет истории работ и версий.** Есть один `draft.json` на работу; предыдущие версии не хранятся.
- **Нет экспорта из интерфейса.** PDF собирается только через `npm run pdf` или кнопку редактора в dev-режиме.
- **Язык интерфейса смешан:** русский в UI, английский в описании PR и части кода.

### 3.2. Надёжность и проверки

- **9 из 12 проверок красные** (раздел 2). Проверки не зелёные, поэтому их нельзя использовать как гейт.
- **Нет `npm test`, линтера, CI.** Единственная автоматическая проверка — `typecheck` и `build`.
- **Нет тестов для `validateDocument`, `renderDocument` (экранирование HTML) и валидации `/api/works`.** Это главные точки доверия к входным данным.
- **Проверки завязаны на состояние файлов.** Например, `tools:check` ожидает отсутствия PDF, которое меняется после каждой печати.
- **Проверка E05/E06 в браузере — Playwright-скрипт в scratchpad.** Скрипт не лежит в репозитории, повторить его нельзя.

### 3.3. Безопасность

- Утверждение и печать защищены: PDF создаётся только при `approval.json`, совпадающем с текущим `draft.json`.
- Текст статьи и ответ модели считаются недоверенными; `preview.ts` экранирует HTML, ссылки разрешены только по HTTPS.
- API редактора без аутентификации. Vite по умолчанию слушает только `localhost`, поэтому риск есть только при `--host` или при выносе в сеть. Для продукта это блокер.
- Ключ `LLM_API_KEY` в `.env` (в `.gitignore`), в `dist/` и ответах `/suggest` не попадает (проверено в прошлой сессии).
- Модель в `suggest.ts` не имеет инструментов; ответ принимается только как JSON с полем `text`.

### 3.4. Бюджет и учёт расходов

- **Лимит расходится:** `docs/agents-tools/budget.json` — 100 ₽, в GUIDE — 500 ₽.
- **Учёт расходится:** `budget.json` показывает 0 ₽ потрачено, а `building-agents/usage.jsonl` содержит записи реальных вызовов (например, 26.10, 06:26 UTC, 1663 и 2079 токенов).
- **Предложения редактора (`/suggest`) в бюджет не пишутся.**

### 3.5. Документация

- **Нет README:** как установить, как задать `.env`, как запустить редактор, как пройти конвейер.
- **Нет продуктовых требований.** `docs/GUIDE.md`, `docs/LEARNING.md`, `docs/TASKS.md`, `docs/TICKETS.md` описывают учебный процесс, а не то, что должен делать продукт.
- **Дизайн-документы про другое.** `docs/DESIGN.md` и `docs/DESIGN-PDF.md` — разбор чужого дизайн-источника, а не дизайн приложения.
- **Задачи не закрыты.** В `docs/TASKS.md` 9 пунктов открыты: 6 для E01–E06 и 3 для T01, T02, T20. Галочки ставит ученик.
- **Нет лицензии.**

### 3.6. Репозиторий

- Два похожих файла: `docs/agents-tools/building-agents.json` и `docs/agents-tools/document.json`. Они отличаются, какой из них актуален, не ясно.
- Inter-файлы в `public/fonts` (`InterVariable.ttf`, `InterVariable.woff2`, `Inter-OFL.txt`) не используются приложением; удаление ждёт решения.
- Жирного начертания Sligoil нет, bold синтетический.
- В `.idea/` закоммичены служебные файлы IDE.

## 4. План доработки

Порядок важен: сначала зелёные проверки и документация, потом продукт.

### Этап 0. Привести пайплайн в порядок (блокер для всего)

1. Синхронизировать `sourceUrl` в `document.json` с `source.json` или перегенерировать документ. Критерий: `document:check`, `preview:check`, `boundaries:check`, `draft:check` проходят.
2. Исправить `check-agent.ts:55`, чтобы заголовок искался с учётом переносов. Критерий: `agent:check` проходит на текущем PDF.
3. Исправить фикстуры `terms:check` и `report:check`, либо обновить ожидания. Критерий: оба проходят.
4. Привести `tools:check` в соответствие с состоянием: либо проверка ожидает PDF, либо PDF удаляется по процедуре. Критерий: проходит.
5. `tool:check` зависит от внешнего сервиса (HTTP 503). Критерий: проходит при доступном сервисе; при недоступном — понятная ошибка с кодом выхода 0 и пометкой «пропущено».
6. Свести бюджет: один источник расходов, учёт вызовов `/suggest` и `model:check`, один лимит. Критерий: `budget:check` показывает сумму, совпадающую с `usage.jsonl`.
7. Добавить `npm run check` — один скрипт, который запускает все проверки в правильном порядке. Критерий: зелёный прогон на чистом клоне.

### Этап 1. Документация и репозиторий

1. README: установка, `.env`, запуск, конвейер, редактор, проверки.
2. Разделить `docs/`: учебные материалы в `docs/learning/`, продуктовые — в корне `docs/`.
3. Удалить дубликат JSON, когда станет ясно, какой из двух нужен. Удалить Inter-файлы, если они не нужны.
4. Добавить `.idea/` в `.gitignore` и убрать из индекса (только после подтверждения).
5. Добавить `LICENSE`.

### Этап 2. Продуктовый интерфейс

1. Заменить учебный текст на главной и заголовок вкладки на продуктовые.
2. Форма «Сохранить ссылку» — либо запускает агента и показывает статус, либо убирается до готовности.
3. Состояния: загрузка, ошибка, пусто, работа утверждена/не утверждена. Ошибки API показываются пользователю.
4. Редактор доступен в сборке, или явно помечен как «только локально» и скрыт в продакшен-сборке.
5. История версий `draft.json` (хотя бы последние N сохранений).
6. Кнопка «Скачать PDF» для утверждённой версии.

### Этап 3. Тесты и качество

1. Unit-тесты на `validateDocument`, экранирование в `renderDocument`, валидацию `/api/works` и `suggest.ts` (без реального вызова модели, через заглушку).
2. Перенести Playwright-проверку E05/E06 в репозиторий как e2e-сценарий, запускаемый вручную.
3. Линтер и `npm test` в `package.json`.
4. CI на GitHub Actions: typecheck, build, unit-тесты.

### Этап 4. Развёртывание (только если продукт — не локальный инструмент)

1. Выбрать хостинг. Вынести API (`/api/works`, `/suggest`, печать) из `vite.config.ts` в серверный слой с аутентификацией.
2. Хранилище: вместо файлов в репозитории — база или хранилище объектов.
3. Очередь для печати PDF и запуска агента, чтобы UI не ждал модель.
4. Лимиты на расход модели на пользователя и на проект.
5. Аудит логов и доступа.

2. **Нужен ли продукт вне учебного проекта.** Если нет, этап 2 сводится к локальному инструменту с понятным README.
3. **Что делать с `approval.json` и `draft.json` для `building-agents`.** Восстановить, утвердить заново или оставить как есть.
4. **Какой из двух JSON (`building-agents.json` или `document.json`) актуален.**
5. **Бюджет: 100 ₽ или 500 ₽.** И нужно ли учитывать `/suggest` в бюджете.
6. **Отметка ручной сверки при утверждении через UI.** Сейчас UI-утверждение не пишет `report.json`/`manual-review.md`, как и CLI `npm run approve`. Нужно ли это менять.
7. **Передавать ли модели текст статьи для предложений редактора.** Сейчас модель видит только текст блока.
8. **Inter-файлы и bold-начертание Sligoil.** Удалять или оставить.
9. **Тестовая инфраструктура.** Нужна ли она для продукта (этап 3), или достаточно ручных проверок.
