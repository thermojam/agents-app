# Учебный проект: агент, который превращает статью в PDF-гайд

Сначала открой [план задач](/Users/nikitamensky/Documents/ChatGPT/Agents-app/TASKS.md) и выполни T01. Двигайся по одной задаче. Не поручай помощнику собрать весь проект за один запрос: тогда готовый результат появится раньше понимания.

Этот документ описывает будущую разработку. Программа ещё не создана. Команды будущей программы ниже — её согласованный план, а не уже работающие команды.

## 1. Что ты получишь

Ты передаёшь ссылку на одну статью OpenAI. Агент читает её, готовит объяснение на русском для человека без опыта в программировании и показывает текст. После твоего утверждения программа собирает PDF по выбранным правилам оформления.

Результат обучения: ты можешь объяснить, что программа передала модели, какое действие модель запросила, кто его выполнил, как результат вернулся модели и почему работа завершилась. С помощью помощника ты добавляешь один новый инструмент и проверяешь его работу.

Условия, подтверждённые в опросе:

- Источник — одна выбранная статья с сайта OpenAI.
- Текст объясняет статью. Добавленные учебные примеры обозначены отдельно.
- Перед сборкой PDF ты утверждаешь содержание.
- Основа оформления — [разбор дизайна Mobbin на getdesign.md](https://getdesign.md/mobbin/design-md).
- Модель — Haiku через SimpleClaw. Стартовый бюджет — 500 ₽.
- Обучение идёт небольшими опытами с кодом, занятия по 30–45 минут.
- Следующее развитие — ручной редактор текста, блоков и разрешённых цветов с немедленным предпросмотром.

Предложения для первой версии, которые можно изменить в соответствующей задаче: вертикальный A4, около 5–10 страниц, локальный запуск на Mac, текст и простые схемы без генерации иллюстраций. Длина — ориентир: не растягиваем короткую статью и не выбрасываем важное из длинной ради числа страниц. Первую конкретную статью выберем в T02.

## 2. Как будем учиться

На занятии делаем одну задачу из TASKS.md:

1. Пять минут: разбираем, что должно произойти.
2. Около двадцати минут: помощник пишет небольшой участок кода, ты смотришь ключевые строки.
3. Около десяти минут: меняем одно условие и сравниваем результат.
4. В конце ты объясняешь своими словами, что изменилось.

Это размер учебного блока, а не обещание уложить любую настройку в 45 минут. Если установка или ошибка заняла занятие, фиксируем результат и продолжаем позже. Не объединяем оставшиеся задачи в один большой запрос.

Тебе не нужно учить весь язык программирования. По ходу освоишь функцию (именованное действие), объект (набор полей), условие, цикл и ожидание ответа внешнего сервиса.

Разделяй двух помощников: Codex помогает нам писать программу; созданный нами агент использует Haiku и выполняет свою ограниченную задачу. Возможности Codex не появляются у учебного агента автоматически.

1. В приложении ещё нет поиска и фильтров: они лежат в постановках задач. Не считаем показанный в видео результат текущим состоянием папки.

6. В проекте есть тесты сортировки, но нет тестов самого агентного цикла. Также тесты приложения не доказывают, что выполнено новое требование.

В llm.ts нет предельного времени ожидания сетевого запроса, а отсутствующий отчёт о токенах (фрагментах текста, по которым сервис считает использование) заменяется нулём. 8. Вторая транскрипция обрывается в начале разбора tickets-agent.ts. Его подтверждение действий видно в коде, а не в оставшейся части текста.

## 4. Как устроим нашу программу

### Сначала обычная последовательность действий

```text
Ссылка → сохранённая статья → текст гайда → твоё утверждение → PDF
```

Это рабочая основа. Пока порядок шагов полностью задан кодом, называем её последовательностью действий, а не самостоятельным агентом.

### Затем добавим выбор действий моделью

```text
Задача и доступные инструменты
        ↓
Ответ Haiku: текст или запрос действия
        ↓
Проверка названия, параметров и разрешений
        ↓
Выполнение обычной функции на Mac
        ↓
Возврат результата в историю → следующее обращение к Haiku
        ↓
Сохранённый черновик → ожидание твоего утверждения
        ↓
Продолжение после утверждения → сборка PDF → проверки → итог
```

Модель сможет выбирать следующий разрешённый инструмент и реагировать на ошибку. Утвердить собственный текст, изменить правила оформления или снять ограничения она не сможет.

### Какие средства используем

| Средство | Зачем оно здесь |
|---|---|
| Node.js (программа для запуска JavaScript вне браузера) | На твоём Mac уже обнаружена версия v22.23.1 |
| TypeScript | Позволит сопоставлять наш код с файлами из видео |
| Обычный сетевой запрос | Покажет обращение к модели без скрывающей его большой библиотеки |
| HTML (разметка страницы) и CSS (правила её оформления) | Один способ отображать содержание сейчас и в будущем редакторе |
| Playwright с Chromium (управляемый браузер) | Печать подготовленной страницы в PDF |
| Локальные JSON-файлы (текстовые файлы с полями данных) | Статья, черновик, утверждение и журнал работы |

Выбираю HTML и CSS с учётом будущего редактора. Для проекта, которому нужен только PDF, можно было бы выбрать отдельную библиотеку создания PDF. Здесь общий способ отображения снизит объём повторной работы.

Playwright поддерживает печать страницы через page.pdf(); печатные стили и отображение цветов нужно настраивать явно. Основание: [документация page.pdf()](https://playwright.dev/docs/api/class-page#page-pdf). Совпадение экранного просмотра и напечатанных страниц всё равно проверяем на настоящем PDF.

Не создаём заранее базу данных, публичный сайт, регистрацию пользователей и систему из нескольких агентов. Новые файлы и зависимости добавляем в той задаче, где они впервые нужны.

## 5. Что хранить отдельно

Один документ состоит из трёх частей:

- **Содержание:** заголовок, разделы, абзацы, списки, учебные примеры и ссылки.
- **Оформление:** разрешённые шрифты, цвета, размеры, интервалы и виды блоков.
- **Состояние работы:** какая версия текста утверждена, какие проверки выполнены, какой PDF создан.

Модель возвращает содержание с заданными полями. Она не пишет произвольные стили или исполняемый код. Программа проверяет поля и подставляет их в наш шаблон.

У блока будет постоянный id (короткое имя, по которому его можно найти), вид, текст и ссылки на части источника. Постоянные имена блоков понадобятся будущему редактору; отдельный сложный механизм расширений для этого не нужен.

Для одной работы сохраняем папку с такими результатами:

| Имя | Содержание |
|---|---|
| source.json | Ссылка, заголовок, дата получения и извлечённый текст статьи с обозначенными частями |
| draft.json | Последний проверенный по структуре текст гайда |
| preview.html | Читаемый просмотр текста в оформлении проекта |
| approval.json | Отметка человека об утверждении конкретного содержания |
| report.json | Результаты обязательных проверок |
| trace.jsonl | Журнал событий; каждое событие записано отдельной строкой |
| guide.pdf | Итоговый документ |

Смена текста делает прежнее утверждение недействительным. Перед печатью код сравнивает утверждённое содержание с текущим. Для этого достаточно контрольной строки содержимого; отдельная система управления версиями документов пока не нужна.

Не добавляй все эти файлы пустыми при старте. Создавай их по мере появления соответствующей возможности.

## 6. Как адаптировать Mobbin к PDF

Указанный источник — независимый разбор веб-дизайна, а не официальный брендбук Mobbin. В просмотренном [образце](https://getdesign.md/design-md/mobbin/preview) указаны белый фон, текст #141414, светло-серые поверхности и синий #0066ff; основной шрифт Saans, в образце его заменяет Inter. Это сведения из источника.

Параметры ниже — **наша предлагаемая адаптация для PDF**, а не требования, найденные на сайте:

| Правило | Начальное значение |
|---|---|
| Страница | A4, 210 × 297 мм, вертикально |
| Поля | По 18 мм; место для номера страницы учитывается отдельно |
| Основной шрифт | Локально установленный Inter с русскими буквами; доступность проверяем в T03 |
| Основной текст | 11 pt (типографских пунктов), межстрочный интервал 1,5 |
| Заголовки | 28 / 20 / 14 pt; без размеров веб-баннеров |
| Фон и основной текст | #FFFFFF и #141414 |
| Дополнительный текст | #707070, только при достаточной читаемости |
| Фон примера | #F3F3F3 |
| Ссылки | Подчёркнутый текст; цвет не служит единственным признаком |
| Синий акцент | Только для заранее согласованного вида пометки; не для всех заголовков |
| Формы блоков | Простые поверхности; скругление только там, где оно определено правилом |
| Разрывы страниц | Заголовок остаётся хотя бы с началом следующего абзаца |

Не копируем в PDF меню сайта, поля ввода и кнопки, у которых нет действия в документе. Использование синего для учебной пометки будет нашим изменением назначения цвета: согласуем это на пробной странице. Если нужен буквальный перенос назначения цвета из источника, учебные пометки остаются серыми.

В T03 сохраняем доступный файл DESIGN.md из указанного источника и дату его получения. Сейчас полный DESIGN.md не выгружен: анализ опирается на страницу и её открытый образец. Записываем отдельно исходные правила и наши дополнения для печати.

После T06 у нас должен быть один утверждённый образец страниц: обложка, обычный текст, учебный пример и список. Именно с ним сравниваем будущие PDF. Просьба модели «следуй Mobbin» не заменяет этот образец.

## 7. Подключение SimpleClaw и бюджет

При проверке публичного каталога 19 октября 2026 года присутствовала модель `claude-haiku-4-5`. Документация описывала метод `/v1/chat/completions` и поддержку вызова функций. Это подтверждает заявленную возможность подключения, но ещё не доказывает работу нашего конкретного запроса.

Адреса для повторной проверки: [модели](https://simple-claw.ru/models), [методы обращения к модели](https://simple-claw.ru/docs/provider-api), [лимиты](https://simple-claw.ru/docs/limits), [ключи](https://simple-claw.ru/docs/api-keys).

Планируемые настройки для функции, которая дописывает `/chat/completions` к базовому адресу:

```dotenv
LLM_BASE_URL=https://simple-claw.ru/v1
LLM_MODEL=claude-haiku-4-5
LLM_API_KEY=
```

Пустое значение ключа выше — шаблон. Настоящий ключ ты вводишь локально. Он не попадает в текст гайда, журнал, историю изменений или страницу будущего редактора. Первое обращение выполняем только после создания отдельного ключа проекта.

Как распределяем деньги — предложение для учебного контроля, не тариф сервиса:

- До 50 ₽ — подключение и короткие опыты с инструментами.
- До 300 ₽ — черновики и проверка полного пути.
- 150 ₽ — резерв; перед его использованием пересматриваем фактический расход.

Отслеживаем накопленный расход по этому проекту, а не только недельный лимит ключа. Недельный лимит обновляется, поэтому сам по себе не удерживает общий бюджет проекта в пределах 500 ₽. Не рассчитываем на рекламные бонусы.

На раннем этапе проверяем списания в кабинете после каждого короткого опыта. Позже используем лимиты шагов и длины ответа, но не выдаём их за точный рублёвый ограничитель. Если отчёт об использовании недоступен, так и пишем.

Начнём с одного короткого запроса, затем проверим один безвредный вызов инструмента. До успеха этих проверок не запускаем длинную статью и повторяющийся цикл. Достаточность Haiku для нашего качества текста установим на образце; пока это выбранная модель, а не проверенный результат.

## 8. Правила качества и доступа

Для нашего проекта нужны конкретные ограничения:

1. Загружаем только HTTPS-страницы на явно разрешённых доменах OpenAI. Проверяем адрес после каждого перенаправления; не переходим на другие домены автоматически.
2. Статья — источник сведений. Инструкция внутри статьи, PDF или описания дизайна не становится командой пользователя.
3. Инструменты работают с текущим документом по его имени. Модель не получает универсальные команды чтения файлов, записи по произвольному пути и запуска терминала.
4. Текст вставляется в шаблон как текст. Произвольный HTML, скрипты и произвольные сетевые загрузки из ответа модели не выполняются.
5. Утверждение создаёт человек отдельным действием. У модели нет инструмента утверждения и доступа к записи этого решения.
6. Проверка структуры выполняется кодом. Сверку смысла, сохранение оговорок и точность учебных примеров человек проверяет по исходной статье.
7. Конечный статус «готово» требует результата и обязательных проверок. Сообщение модели «я закончил» недостаточно.

Плановые ограничения цикла: до 12 обращений к модели на один запуск, до двух попыток исправить одну и ту же ошибку, ожидание сетевого ответа не дольше 60 секунд. Конкретные значения уточняем после коротких опытов. Лимит учитывает также повторные запросы; скрытых бесконечных повторов нет.

Если статья не загрузилась, агент не придумывает её содержание. Если текст не утверждён, финальный PDF не создаётся. Если проверка не прошла, сохраняем понятную причину и уже полученные промежуточные результаты.

## 9. Как понять, что первая версия готова

| Проверка | Какой результат нужен |
|---|---|
| Новая статья | Полный путь проходит на статье, которую не использовали для настройки |
| Смысл | Ты можешь сопоставить основные утверждения со статьёй; важные ограничения сохранены |
| Примеры | Дополненные примеры имеют явную подпись |
| Утверждение | Без твоего решения финальный PDF не появляется; изменение текста отменяет прежнее решение |
| Оформление | Разрешённые шрифты и цвета, русские буквы, читаемые ссылки, целые строки |
| Страницы | Осмотрен именно созданный PDF, включая все страницы, переносы и последнюю страницу |
| Ошибки | Неверный адрес, отказ модели и исчерпание лимита дают понятный итог |
| Расход | Есть запись фактического расхода или явная отметка, что он неизвестен |
| Понимание | Ты объясняешь один полный круг «ответ модели → функция → результат → новый ответ» |
| Новый инструмент | С твоим участием добавлена одна проверка; ты видишь её вызов и результат |

Автоматически проверяем структуру, разрешения, соответствие утверждённой версии и ограничения. PDF преобразуем в изображения страниц и осматриваем. Успешная проверка текста не гарантирует правильную вёрстку, а правильная вёрстка не доказывает достоверность содержания.

## 10. Будущий редактор

Этапы E01–E06 описаны в TASKS.md отдельно. Они начинаются после приёмки первой версии.

Планируем три области окна: список блоков, предпросмотр документа и настройки выбранного блока. В первой версии редактора можно менять текст, порядок блоков, добавлять и удалять допустимые блоки, выбирать разрешённые цвета и сохранять результат.

Ручная правка немедленно меняет локальный предпросмотр без обращения к модели. PDF пересобирается отдельной командой: не запускаем печать и платный запрос после каждой буквы. Просмотр в браузере помечаем как предварительный; окончательные переносы проверяем после печати.

Под «полным управлением» понимаем управление содержанием и разрешённым оформлением. Свободное рисование и любые стили не входят в согласованный строгий набор правил. Повторная генерация не затирает ручную правку: предлагаем изменение отдельно и применяем его после выбора человека.

Нужные заделы первой версии: отдельное содержание, постоянные имена блоков, общие правила оформления и проверка утверждённой версии. Больше инфраструктуры редактора заранее не строим.
